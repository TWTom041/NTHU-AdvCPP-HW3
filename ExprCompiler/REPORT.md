# HW3 報告：Expr → Brainfuck 編譯器

## 成果摘要

- `make test`：51 項全數通過（含 26 項錯誤處理）。
- `make cases`：44 組全數通過，總執行步數 **120,041**。
- 編譯器為單一檔案 `expr.cpp`，只使用 C++20 標準函式庫，沿用原本的 Makefile。

## 整體架構

```
原始碼 ─► 詞法分析 ─► 遞迴下降語法分析 ─► 符號執行（多項式 mod 256）
      ─► 分析（來源 / 一元函數表）─► 記憶體配置搜尋 ─► 產生 Brainfuck
```

### 1. 詞法與語法分析

- 每行獨立處理，`#` 之後為註解。只接受規格中的字元，其餘字元回報 `unsupported character`。
- 遞迴下降的函數與 EBNF 一一對應：`expression → term → unary → primary`。優先序與結合方向由呼叫層次自然決定，連續一元運算以迴圈處理，避免深度遞迴。
- 所有錯誤都會在輸出任何 Brainfuck 之前，以 `Error: line N: 原因` 印到 stderr，並 `return 43`。

### 2. 符號執行：不建語法樹，直接算出多項式

Expr 沒有分支或迴圈，因此每個變數在任何時刻都是 `input()` 值的多項式（mod 256）。編譯器在編譯期就把整個程式「執行」一次：

- 值表示為「原子」（atom）的線性組合加常數。原子是輸入值，或兩個仿射式的乘積。
- 乘積的兩個運算元先正規化：提出 2 的冪次與單位元倍數，挑選係數成本最低的代表式。之後依運算元做 hash-consing，因此 `a*b`、`b*a`、`(2a)*(3b)` 會共用同一個乘積原子。
- 這一步同時完成常數摺疊、常數傳播、死碼消除、共同子運算式消除，以及 `a*16*16 = 0` 這類代數化簡。賦值本身在執行期完全不花步數。

### 3. 分析：一元函數表

- 只依賴單一執行期儲存格的原子（例如 `c*c`、`(a+5)*(a-3)`）就是該格的一元函數。編譯器會預先算出 256 個值的查表。
- 「來源」（source）指執行期真的存在的值：輸入，以及需要真正執行乘法的乘積。
- 每個目標格（輸出格或乘法器的運算元埠）從每個來源收到的貢獻，都表示成一張 256 項的表。

### 4. 程式碼產生

**串接（cascade）技巧**：對儲存格 `x` 產生 255 層巢狀的 `x[-`。當 `x` 歸零時，程式執行到的位置剛好「知道」`x` 的值。最深那一層的 case（由旗標保證只執行一次）可以把任意常數 `f(x)` 加到任意多個格子。成本約為每單位 6 步，加上一次常數加法，與函數的複雜度無關。

每個來源依估計成本選擇分配方式：

- **迴圈分配**：適用於線性且係數小的情況。大係數會規劃成經過暫存格的乘法樹，例如 ×173 拆成 ×13 再 ×33。
- **串接分配**：適用於非線性或係數大的情況。

**乘法**：對一個運算元做串接，得到常數 `u` 後，用預先算好的最佳鏈 `u = a + f·(b + g·h)`，以最多三個迴圈把 `u·V` 加進結果。

其他細節：

- 只用一次的輸入直接 `,` 讀進目標格。只送到單一輸出的乘積直接累加在輸出格。
- 輸出常數與運算元常數會併入某個串接的查表中。輸出時只需移動到該格、調整常數差、再 `.`。

### 5. 記憶體配置

每個邏輯儲存格在事件時間軸上都有存活區間，存活區間不重疊的格子可以共用位置。配置方式如下：

- 用區域搜尋調整乘法區塊位置、鏡像方向、輸出格與輸入格，最小化估計的指標移動步數。
- 指標移動由產生器追蹤，只輸出必要的 `<`/`>`。

## 正確性驗證

除了官方測試，另外做了以下驗證：

- **差分測試**：隨機產生 2,000 多個程式，與 Python 參考實作比對輸出，涵蓋多個輸入、乘法、平方、相消為 0 的運算式、未使用的輸入等情況。
- **乘法器窮舉**：每個運算元都測遍 0–255，對方運算元取特殊值與隨機值，共 5,120 組，含平方。
- **退回路徑**：把程式碼預算設為 0 強制使用小程式碼的退回路徑，再跑一次差分測試。
- **Sanitizer**：用 AddressSanitizer / UndefinedBehaviorSanitizer 編譯，跑官方測試與差分測試。
- **壓力測試**：10,000 個變數、500 層括號、300 個串連乘法、5,000 個輸出。每個都在 0.7 秒內編譯完成，執行結果正確。

## 程式碼大小的取捨

串接會產生大量程式碼。助教的執行器每個指令約需 32–64 bytes 記憶體，因此設定了上限：

- 單一串接最多約 200 KB，全部串接合計約 2 MB。
- 超過上限時，線性來源改用迴圈，非線性來源改為「串接進少數中繼格，再用迴圈分配」，乘法改用約 1 KB 的 base-4 移位相加乘法器。
- 壓力測試中，最大輸出從未設限時的 17 MB（執行器約 1 GB 記憶體）降到 3.2 MB（約 134 MB）。

## 尚可改進之處

- 若乘法的一個運算元只是某個輸入的函數，可以把乘法直接合併進該輸入的串接，省下一次串接（約 768 步）。這需要重新排定各來源的處理順序，尚未實作。
- 配置搜尋使用平均值估計（假設輸入均勻分布），沒有針對實際輸入分布調整。

## 個人心得

### 看起來難的部分，其實不難

第一次看到「把運算式編譯成 Brainfuck」，直覺會覺得很難。Brainfuck 只有八個指令，沒有暫存器、沒有定址、也沒有乘法。讀取一個值就會把它破壞掉，還要自己處理運算子優先序、一元負號、結合方向，以及附帶行號的錯誤處理。

不過計算機程式設計課有一份很類似的作業：把運算式編譯成組合語言。那份作業已經走過完整的流程：切 token、遞迴下降分析、建語法樹、後序走訪產生指令、分配暫存器。這次幾乎可以一對一對應過來：

- 暫存器換成記憶體格；
- load/store 換成「搬移並複製」的迴圈；
- 暫存器分配換成記憶體格分配。

作業提示說「約 300 行可以完成」，對照那份作業也很合理。有些地方甚至比組合語言簡單：每個運算都要 mod 256，而 Brainfuck 的格子本來就是 uint8 會自動溢位，等於免費做到；錯誤處理也只需要「回報行號，並以 43 結束」。所以只求正確的話，這份作業並不難。

### 真正花心思的是優化

有難度的是排名分數，也就是要讓執行步數越少越好。這裡從組合語言帶來的直覺反而會誤導：

- 在組合語言裡，我們在意的是指令數量。Brainfuck 的成本卻和「執行時的值」成正比：搬一個值要跑「值」那麼多次迴圈，乘以常數 c 每次還要多 c 個 `+`，指標移動也算步數。
- 寫出短的程式不代表跑得快。最後用的串接技巧剛好相反：用大量程式碼換取很少的執行步數。

幾個比較重要的領悟：

1. **沒有控制流程，就能在編譯期把程式算完。** Expr 沒有 if 和迴圈，所以每個變數都只是輸入的多項式，唯一未知的是 `input()` 的值。想通之後，「變數存在哪一格」這個問題就消失了，賦值完全不需要產生程式碼。
2. **先量測再優化。** 我原本以為記憶體配置（指標移動）是主要瓶頸，花工夫做了配置搜尋，結果只少了約 1%。剖析每段程式的實際步數之後才發現，真正的成本在「把一個值用各種係數送到很多格子」和乘法。把這兩者換成串接之後，步數一口氣從 64 萬降到 21 萬。
3. **有些看起來漂亮的數學在 mod 256 下不成立。** 平方差乘法在整數上很好用，但 `x+y` 的進位資訊在 8 位元格子裡已經遺失，造成 128 的誤差。這個問題要實際推導才會發現。
4. **優化會碰到現實限制。** 串接讓步數大幅下降，但壓力測試時產生了 17 MB 的程式，助教的執行器要用將近 1 GB 記憶體。所以必須設定程式碼大小上限，並保留小程式碼的退回路徑。「最快」並不等於「最好」。

### 關於正確性與 AI 輔助

優化越激進，越容易出錯。例如串接利用指標漂移的技巧、多個格子共用記憶體，都很容易出現邊界錯誤。實際上，第一版配置就曾出現旗標格和輸入格重疊的錯誤，只在一組測資上算錯。光靠官方的 44 組測資不夠，大量的隨機差分測試才是信心的來源。

使用 AI 輔助之後，我的工作重心從「逐行寫程式」變成三件事：判斷方向是否合理、解讀剖析數據、確認驗證是否充分。AI 能很快寫出複雜的實作，但「要優化什麼」「怎麼證明它是對的」仍然需要清楚的判斷。這是這份作業讓我收穫最多的地方。

## AI 使用揭露

本作業使用 AI （oh my pi + opus 5.5）輔助，使用範圍如下：

- **設計討論**：與 AI 討論編譯流程，包括語法分析、符號執行、乘法與分配策略、串接技巧與記憶體配置。
- **程式實作**：`expr.cpp` 的程式碼主要由 AI 在對話中撰寫，並依剖析結果逐步修改與優化。
- **測試**：差分測試、乘法器窮舉測試、壓力測試與 sanitizer 檢查的腳本由 AI 撰寫並執行（皆為一次性腳本，未納入繳交檔案）。
- **文件**：本報告是由我先寫出一個非常雜亂無章的文件，再由 AI 產生出一個比較好讀的文章。
